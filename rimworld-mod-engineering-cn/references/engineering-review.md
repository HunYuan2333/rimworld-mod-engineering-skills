# 工程审查与侵入性评估

## 证据纪律

按以下顺序审查事实：源码、发布程序集/反编译、XML 与加载布局、日志和可复现行为、作者文档、第三方报告。反编译 C# 可揭示控制流、Patch 目标、状态所有权和持久化，但不是规范源码：名称可能由工具生成，部分 IL 可能无法还原，注释和构建配置通常缺失。

不得根据平衡、题材、流行度、国别或“军备竞赛”推断动机、伦理或代码质量。将担忧转换成可观察技术属性。

架构审查同时阅读 [engineering-philosophy.md](engineering-philosophy.md)。区分：

- **缺陷**：可达路径违反已声明不变量；
- **未受控风险**：设计缺少与其影响范围相称的顺序、所有权、隔离、迁移或诊断；
- **受控妥协**：深层技术确有必要，并具有相称控制；
- **风格差异**：不影响实质不变量、支持承诺或维护属性。

## 侵入性维度

每项按 `0 无`、`1 局部`、`2 子系统`、`3 全局/替换` 评估并引用证据：

| 维度 | 问题 |
|---|---|
| Patch 广度 | 修改了多大范围的游戏或其他 Mod 表面？ |
| Patch 深度 | 公开扩展点、方法拦截、私有访问还是 IL 替换？ |
| 依赖耦合 | 多少必需/可选外部契约可能破坏它？ |
| 全局修改 | 是否改变基础 Def、全部 Humanlike、战斗规则、派系或共享 Registry？ |
| 持久状态 | 多少状态保存在存档、地图、世界对象、任务或引用中？ |
| 热路径暴露 | 是否在每帧/Tick/Pawn/Projectile 或全局生成/战斗路径运行？ |
| 可逆性 | 升级、禁用或移除是否会损坏存档或改变其语义？ |
| 兼容表面 | 承诺支持多少版本、DLC 和 Mod 组合？ |

不要机械相加形成“好/坏”分数。用轮廓要求相称控制。

## 相称控制

- 宽 Patch：明确目标清单、Patch 顺序诊断、代表性组合测试。
- 深 Patch：版本锚点、可见匹配失败、上游差异审查。
- 大量集成：条件目录/程序集、适配器、兼容性所有权矩阵。
- 全局 Def 修改：原值基线、幂等应用、重启政策。
- 持久系统：schema 版本、迁移、引用修复、移除政策。
- 热路径：Profiler 证据和有界工作。
- 低可逆性：清晰元数据/文档及可行的迁移工具。

## 去命名化反例

以下用于说明失败机制，不用于否定整个项目。

### 只有扫描、没有安装协议

某大型大改扫描全部已加载程序集，构造每个兼容类，再按枚举顺序调用能力检查和安装。扫描时处理了类型加载异常，但构造和安装没有逐参与者隔离；协议也没有稳定身份、依赖、顺序、重复和状态契约。

风险：一个可选集成会阻止后续集成安装，正确性可能依赖未规定的程序集/类型顺序。结论不是“禁止反射”，而是让发现与激活成为确定、可诊断、故障隔离的生命周期。

### 业务删除没有释放生命周期所有权

某持久种族/派系系统将选定 WorldPawn 永久保留以供以后返回。一条重置路径会把它们交还游戏丢弃决策，但过期路径只从 Mod 集合中移除。

风险：业务状态认为 Pawn 已消失，游戏仍永久持有它。必须显式建模所有权转换并审查每个退出路径，而不是只清空列表。

### 日志限流没有声明作用域

静态按 Key 限流器在固定次数后阻止刷屏，但没有重置边界。

风险：后续存档或重载中的故障会在本进程余下时间被隐藏。应保留限流机制，但声明其作用域是突发、Map、Game、加载周期还是进程。

### 全局回调没有所有权

兼容表面暴露公开可变静态回调列表。参与者追加委托，但注册没有身份、去重、优先级、异常隔离或移除。

风险：重复初始化导致重复效果，一个回调破坏整条链，委托超过所有者寿命。即便初始实现只是列表，也应把注册视为有生命周期的 API。

### 含义模糊的“原始值”

设置系统捕获武器字段、修改已加载 Def，并在以后恢复捕获值。在共享进程中，捕获基线可能已经含早期 Mod 修改，而恢复又可能覆盖后续修改。

风险：局部正确的 Reset 仍会破坏跨 Mod 组合。应声明基线阶段、确定顺序、诊断来源和重启/重载政策。见 [configuration-def-transforms.md](configuration-def-transforms.md)。

### 本地构建修补掩盖环境耦合

工程引用某位开发者的绝对游戏/Workshop 路径，并直接构建进可游玩 Assemblies 目录。构建后会删除一个已知陈旧 DLL，以避免版本混合。

删除动作是有价值的控制，但构建仍不可复现，其他陈旧产物也可能残留。应分离可配置依赖解析、确定性 Staging 和最终产物审计。

## 反编译样例

以下样例来自 RimWorld 1.6 发布程序集。数量只表示表面范围，不是质量分数。

### 样例 A——地图级设施模拟

主程序集目标为 `net472`；反编译约 257 个 C# 文件、2.4 万行。包含两个地图组件、大量对象组件、46 个持久化相关文件、38 个 Tick 相关文件、18 个特性声明 Harmony 目标、若干手工条件 Patch 和一个 Transpiler。

观察到：

- 对象向地图所有的网络服务注册和注销；
- 每种管线类型使用脏标记推迟完整网格重建；
- MapComponent 拥有格子网格、网络实例和地图生命周期；
- 静态字典加速 MapComponent 查询，并在地图移除/游戏销毁时清理；
- 显式映射旧类型名和 Def 名；
- 可选功能在启动阶段条件安装 Patch。

可复用经验：地图模拟适合地图所有权、显式注册、脏失效和销毁。审查逐 Tick 网络工作、完整重建触发、静态缓存清理、多人确定性和仅启动生效的设置。

### 样例 B——派系、叙事与战斗套件

主程序集目标为 `net48`；约 418 个 C# 文件、4 万行。约 50 个特性 Harmony 目标、两个 Transpiler、69 个持久化相关文件、42 个 Tick 相关文件、多个游戏/世界 Manager 及多个独立集成程序集。

观察到：

- GameComponent 协调战役、叙事、头衔、特殊 Pawn、支援和结局 Manager；
- 显式表示旧组件迁移；
- 事务逻辑保存资源快照，并分离验证与消耗；
- 条件集成与常驻程序集物理分离；
- 线程局部上下文包围递归/全局 Raid 选择状态；
- Patch 涉及 Pawn 生成、伤害、死亡、工作、派系变化、Raid、精神状态、渲染、贸易、头衔和妊娠。

经验：宽内容套件需要 Manager 边界、迁移所有权、事务资源变更和隔离集成。审查共享方法冲突、Manager 顺序、引用修复、递归上下文清理、热路径成本和完整存档升级矩阵。

### 样例 C——军备与自定义机制套件

主程序集目标为 `net48`；约 366 个 C# 文件、4.7 万行。约 25 个特性 Harmony 目标，主程序集未观察到 Transpiler，53 个持久化相关文件、55 个 Tick 相关文件，并有独立战斗/动画集成程序集。

观察到：

- 带版本的 GameComponent 保存载具、商人、折扣、槽位、冷却等全局状态，并执行显式迁移；
- 设置扫描选定武器 Def，保存伤害、冷却、标签基线并重新应用配置；
- 通过反射访问私有 Projectile 字段以全局修改 Def；
- 创建视觉缓存或加载 Shader 前检查 Unity 主线程；
- Patch 涉及 Health、Hediff、精神状态、寻路成本、Projectile 发射/拦截、Explosion、Power、Raid、地图移除、射程和武器绘制。

经验：运行时 Def 重写需要不可变基线、幂等 Apply/Reset、明确应用阶段和兼容性所有权。审查私有字段漂移、重复应用、设置 UI 副作用、主线程资源创建、全局方法冲突和持久自定义对象的移除/迁移。

## 审查输出

结论包含：

- 已验证事实及源码/反编译限制；
- 各维度侵入轮廓；
- 具体失败方式，而非笼统标签；
- 已有控制优势；
- 缺失控制或测试；
- 会改变架构的问题。

审查修复方案时还要说明它恢复哪个不变量、是否改变权威来源或生命周期，以及修复后仍处于哪个妥协层级。局部所有权、顺序或清理修正足够时，不建议宽泛重写。
