# XML、Def 与内容工程

## 先建立内容图

把内容视为由稳定 ID 连接的图，而不是独立 XML 文件。确认：

- Def 的所有引用和被引用关系；
- 研究、配方、工作台、材料、产物和获取路径；
- PawnKind、Faction、Trader、Incident、Quest 与生成入口；
- DLC、Biotech 基因、Ideology/Royalty 机制等条件边；
- 贴图、声音、Shader、Style、BodyType 和 ApparelLayer 资源路径。

玩家可看到 Def 不代表能够在正常游戏中获得它。验证从游戏入口到内容结果的完整可达性。

## 标识与继承

- 已发布的 `defName`、包 ID、类型名和存档键是持久化身份，不要随意改名。
- 改名时提供对应的旧名映射、迁移或兼容 Patch。
- 使用抽象父 Def 消除真正共享且同步变化的字段；不要建立难以追踪的深继承树。
- 为公开 Def、配置键和跨 Mod 标签使用唯一前缀。
- `label` 和翻译文本不是身份，不要用显示文本识别内容。

## XML Patch

优先添加新 Def、继承和窄条件 Patch。编写 Patch 时：

- 使用足够精确且稳定的选择器；
- 明确目标不存在时是允许跳过还是应当报错；
- 避免依赖另一个 Mod 的显示顺序或非契约内部结构；
- 使用依赖/DLC 条件，确保可选内容缺失时不会解析其类型；
- 检查重复节点、重复 `defName`、错误父类和 PatchOperation 失败日志；
- 对替换或删除操作说明与其他 Patch 的组合语义。

不要复制整份上游 Def 只为修改少量字段；这会冻结其他字段并增加升级冲突。

## 内容与 C# 的边界

静态数据和已有 Worker/Comp 能表达的行为留在 Def/XML。只有在需要运行时状态、算法、生命周期或真正的新扩展点时引入 C#。

把平衡数值留在 Def 或设置中，把不变量和状态转换放在代码中。不要让 Harmony Patch 承担本可由 Def 配置表达的内容差异。

## 条件内容与版本目录

- 用 `LoadFolders.xml` 隔离不同游戏版本、DLC 和可选依赖的 XML/程序集。
- 依赖缺失时，加载器不应看到含外部类型的 XML 或程序集签名。
- `loadAfter` 不等于依赖声明。
- 多版本共用内容时确认 API、Def 字段和资源格式确实兼容；不要只因为能启动就认为兼容。

## 内容验证

至少检查：

- 干净启动无红字、Def 错误和 Patch 失败；
- 研究、配方、工作台和产物链可达；
- 生成、装备、掉落、销毁和本地化；
- 各支持 DLC/依赖组合；
- 缺失可选内容时的行为；
- 存读档和已发布身份兼容；
- Linux 大小写敏感路径；
- 最终打包目录中的真实资源，而不是源码路径。
