# 工程哲学与决策规则

架构、重构、设计审查或主要风险来自耦合而非单个机制时使用本参考。它是决策框架，不要求把每个 Mod 都改造成框架。

## 核心原则

1. 改善结构前先保护行为和数据。
2. 让重要状态、依赖、阶段和失败方式显式化。
3. 业务策略属于拥有它的功能；共享基础设施保持中立。
4. 优先选择可逆、可观察的变更。刻意不可逆时明确说明。
5. 工程投入与影响范围匹配。小型内容变更需要稳定标识和验证；替换级系统需要契约、迁移、诊断和兼容性所有权。
6. 根据后果是否受控评价技术，不根据标签。反射、静态状态、Harmony、Manager 和 Def 修改都可能合理，但必须明确范围与生命周期。

## 从不变量开始

先写无论如何都必须成立的事实，例如：

- 一个请求最多提交一次；
- 一个对象同一时刻只有一个生命周期所有者；
- 批处理失败时要么完全不改，要么其已声明的成功子集稳定成立；
- 派生状态总能从声明的权威来源重建；
- 禁用可选集成不会禁用无关功能；
- 存档要么迁移到新 schema，要么可见地失败，不能被部分重新解释。

在成功、拒绝、取消、异常、超时、存读档、重载、依赖缺失和重复回调路径中验证不变量。测试应面向这些性质，而不是复刻方法实现。

## 权威状态与派生状态

每项可变事实指定一个权威来源，其他表示形式是视图、缓存、索引、投影或传输快照。

| 状态类型 | 要求 |
|---|---|
| 权威状态 | 一个所有者控制修改并定义事务语义 |
| 持久化状态 | 明确 schema、默认值、迁移、身份和内容缺失行为 |
| 派生状态 | 明确来源、重建阶段、失效触发和陈旧读取政策 |
| 外部状态 | 明确信任边界、校验、超时、重试和核对 |
| UI 状态 | 反映领域状态，不制造确认，不绕过状态转换 |

只有同步方式也是设计的一部分时，才允许重复可变状态。“通常会一起更新”不是一致性模型。

## 内聚

当一个组件的成员因相同领域原因变化，并共享同一所有者和生命周期时，它具有高内聚。优先按功能内聚，不按技术名词堆放文件。

出现以下情况时考虑拆分：

- 游戏规则与 UI、持久化、传输或兼容策略混合；
- 同时拥有不同寿命的状态，例如进程缓存和存档数据；
- 因互不相关的功能变化；
- 测试或替换时必须构造无关系统；
- 协调器同时完成所有参与者的具体工作。

不要只为缩短文件而拆分。大型但内聚的状态机，可能比一群依赖隐藏调用顺序的服务更安全。

## 耦合

按耦合形式审查，而不是只数引用：

| 耦合 | 常见症状 | 优先控制方式 |
|---|---|---|
| 编译期 | 必需外部类型泄漏进核心签名 | 契约程序集或适配器；必需依赖保持显式 |
| 时间顺序 | 调用必须按未记录顺序发生 | 生命周期阶段、状态机或依赖图 |
| 状态 | 多个模块修改同一集合或标志 | 单一权威来源和命令/事件 |
| 行为 | Patch 依赖上游未公开副作用 | 记录必须保留的契约和版本锚点 |
| 数据形状 | 存档/设置依赖类型或字段名 | 稳定 ID、schema 版本、迁移 |
| 全局 | 静态注册表、Def 数据库、共享随机流 | 作用域、确定顺序、清理 |
| 故障 | 一个可选组件终止无关初始化 | 逐组件隔离和依赖感知阻断 |

目标不是零耦合。功能必然需要耦合；架构应将其放在刻意、可检查的接缝上。

## 依赖方向与分层

常用默认结构：

```text
功能策略 -> 契约 <- 适配器/集成
                ^
          组合与生命周期
```

- 除非这本身就是领域，领域策略不应了解 Harmony 目标、XML Patch、网络包、窗口或某个可选 Mod。
- 适配器负责翻译外部语义，不得静默削弱领域不变量。
- 组合根发现具体参与者、排序和注入依赖；它负责协调，不吸收功能逻辑。
- Shared/Common 代码必须足够中立和稳定，才能承受其依赖引力。不要因为有两个调用者就移动进去。
- 同级功能可以直接共享小型契约；不要强迫宿主成为所有业务协作的中介。

## 按压力选择模式

| 实际压力 | 可选模式 | 注意事项 |
|---|---|---|
| 可选外部 API | Adapter / 防腐层 | 不要用反射隐藏真实必需依赖 |
| 多个贡献者 | Registry / Pipeline | 定义身份、顺序、重复策略、隔离和所有权 |
| 多阶段行为 | 显式状态机 | 避免布尔组合产生非法状态 |
| 昂贵派生视图 | Cache + Invalidation | 声明作用域和重建权威 |
| 原子资源修改 | Transaction / Unit of Work | 定义回滚和结果未知处理 |
| 多种构造策略 | Factory | 靠近真正变化的构造政策 |
| 跨功能通知 | Event Stream / Observer | 订阅寿命和异常隔离属于契约 |
| 算法族 | Strategy | 不为单个稳定实现制造接口 |

设计模式是词汇，不是合规徽章。不能隔离变化、澄清所有权或带来有意义测试的抽象应被拒绝。

## 初始化拓扑

用有明确输入输出的阶段描述初始化。大型 Mod 可能采用：

```text
发现 -> 验证 -> 注册 -> 转换 Def -> 建立缓存 -> 激活 -> 运行
                                                -> 诊断
运行 -> 停用 -> 注销 -> 释放
```

具体阶段可以不同，但必须处理：

- 稳定参与者身份；
- 依赖和排序规则；
- 重复注册政策；
- 幂等性或明确的一次性保证；
- 逐参与者故障隔离；
- 必需依赖失败后的下游阻断；
- 有依赖关系时按逆序清理；
- 可见的阶段和失败状态。

正确性依赖顺序时，不得依靠文件系统、`AppDomain.GetAssemblies()`、反射类型、Harmony 偶然顺序或未声明的长事件排序。

## 工程例外

兼容或替换范围要求突破首选边界时，记录简短决策：

- 要保护的不变量或能力；
- 跨越的边界及浅层接缝不足的原因；
- 受影响版本和集成；
- 隔离与失败行为；
- 测试和诊断；
- 负责人及重新评估/移除条件。

例外应局部且可搜索。重复压力出现前，不要把一次性 workaround 泛化成共享抽象。

## 完成定义

根据风险，完成应意味着：

- 行为、非目标、支持矩阵和不变量已说明；
- 依赖方向和状态所有权可检查；
- 初始化、配置和清理行为已定义；
- 存档、配置和 API 兼容已处理或明确不支持；
- 故障可隔离、可诊断；
- 热路径和全局影响有基于证据的检查；
- 已测试最终打包产物；
- 刻意妥协有边界记录。
