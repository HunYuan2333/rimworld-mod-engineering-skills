# 框架与基础设施项目类型

只在处理框架/基础设施核心或明确接入其扩展的 Mod 时使用。未覆盖部分仍遵循通用规则。

## 项目意图

样例 F 主要是框架/基础设施，而非游戏内容大改。保持这一区别：客户端系统、契约、扩展加载、服务边界、UI、网络和可观测性不得静默吸收平衡或内容策略。

修改前阅读仓库当前指令、设计哲学、开发者指南和兼容边界文档。发生冲突时，以仓库当前文档为准。

## 基础边界

- 客户端和服务端/工具可以使用不同目标框架；不得让仅服务端 API 泄漏进游戏客户端。
- 依赖指向契约；Loader、网络传输、游戏适配器、持久化和 UI 位于领域策略外层。
- 新增功能优先通过扩展/插件注册，不为每个附加功能修改核心开关。
- 显式生命周期：发现、验证、加载、初始化、运行、停止、失败。
- 隔离扩展故障，使一个可选插件不能禁用无关功能。
- 宿主保持中立；功能业务属于同级扩展或其契约，不属于宿主特例分支。
- 同级扩展通过自己的小型契约合作；不要让宿主中转所有业务交互。

## 扩展契约

每个扩展定义：

- 身份、版本、兼容 API/能力范围和依赖；
- 注册与初始化顺序；
- 拥有的资源和清理方式；
- 配置 schema、默认值和迁移；
- 线程亲和要求；
- 面向用户的失败/诊断行为；
- 服务端、依赖或能力缺失时的行为。

语义顺序使用依赖图。检测循环；必需依赖失败时阻断下游；按逆依赖顺序 Shutdown。即便物理加载需要文件名排序，也不能把它作为唯一语义顺序机制。

阶段分离：

- Discovery 定位候选和元数据；
- Registration 贡献 API/Handler，但不启动工作；
- Activation 获取活动服务并订阅；
- Shutdown 反转激活并释放资源。

框架支持运行时管理时跟踪 discovered、disabled、dependency-disabled、registered、active、failed、shutdown 等状态。注册或激活失败后，移除该扩展拥有的贡献，再继续处理无关参与者。

必需框架 API 使用编译时契约。可选或跨版本能力使用 Capability Check/Adapter。不要只为避免声明真实依赖而使用反射。

## 可靠性

限制队列、载荷、重试、超时和日志。外部 I/O 离开游戏线程。后台返回不可变/纯数据，再通过验证过的主线程交接应用，并重新验证游戏状态。

批处理明确选择原子、可重试或尽力而为；部分完成违反一致性时不得静默跳过失败。

适配器只翻译协议/能力差异，不得削弱领域不变量。传输发送、Handler 返回、乐观 UI 更新和权威远端确认是不同事件。结果未知需要核对，不能静默转成成功或安全回滚。

注册、事件订阅、Timer、Queue 和后台工作都需要对称 Shutdown。重复 Activate/Shutdown 或“载入—主菜单—再载入”不能重复 Handler 或保留旧游戏对象。

## 验证

至少测试：

- 无扩展框架；
- 一个有效扩展；
- 非法元数据、依赖或 API 范围；
- 初始化与运行时故障隔离；
- 若支持，启用/禁用/重载生命周期；
- 配置迁移；
- 网络超时、断线和反压；
- 扩展持久化游戏状态时的存读档；
- 实际 RimWorld 构建中的最终客户端程序集。

框架专项测试和示例应与通用 RimWorld 建议分开，使 Skill 仍适用于普通内容 Mod。
