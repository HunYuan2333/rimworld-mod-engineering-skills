# 验证、打包与发布

## Mod 测试层级

根据项目能力选择：

1. 解析器、策略、状态转换、计算和迁移的纯 C# 测试；
2. 重复 Def、缺失父项、错误路径和 Patch 失败的 schema/XML 检查；
3. 针对支持游戏/依赖引用的构建检查；
4. 工作、事件、Raid、Quest、能力、UI 和销毁的开发者模式场景；
5. 存读档 fixture 和版本迁移；
6. 兼容烟雾矩阵；
7. 最终安装包烟雾测试。

不要为了测试简单包装器而模拟整个 Verse。将确定性策略从游戏适配器中提取出来。

按失败风险选择测试形式：

- 纯策略/不变量：普通单元测试或性质测试；
- Def 选择/转换：fixture 数据库或打包启动验证；
- 生命周期/所有权：重复加载卸载、地图移除、过期、取消和清理场景；
- Harmony/私有 API：目标/签名检查和游戏内行为；
- 渲染/UI：多分辨率、缩放、EventType、长内容和 Profiler；
- 兼容：依赖缺失、存在、过期及已知交互组合；
- 打包：启动精确的 Staging 产物。

覆盖率百分比不能很好代表 Mod 风险。一个所有权转换或包冲突测试，可能比大量包装器测试更有价值。

## 兼容矩阵

按风险选择组合，不穷举所有排列：

- 仅核心；
- 每个必需依赖基线；
- 每个支持的 DLC Gate；
- 每个可选集成单独启用；
- 已知相互作用的集成组合；
- 承诺优雅降级时测试依赖缺失/过期；
- 代表性大型玩家 Mod 列表。

不支持的组合写入元数据或文档，不依赖口头知识。

## 发布产物审计

检查真正将发布的目录：

- 每个版本/加载条件只有预期程序集；
- 不包含游戏 DLL、引用程序集、PDB、测试二进制或非预期陈旧重复 DLL；
- `About.xml`、预览图、版本目录和 `LoadFolders.xml` 有效；
- 语言和资源完整，大小写正确；
- 依赖要求的源码/许可证声明完整；
- 版本、变更和迁移说明完整；
- 从打包产物干净启动。

将产物与明确 manifest 或 staging 规则比较。直接构建进可游玩 Mod 目录虽然方便，却可能把当前 XML/资源与旧 DLL 混合；必须刻意检测或删除陈旧输出。

## 可复现构建契约

受支持构建应说明：

- 游戏和依赖程序集版本；
- 如何提供本地引用路径而不提交个人 Steam 路径；
- 目标框架和语言版本；
- clean/build/package 命令；
- 确定性 staging 布局和预期程序集；
- 如何发现陈旧或重复二进制；
- 需要哪些生成或 vendored 输入；
- CI 是否验证与发布相同的产物形状。

绝对 `HintPath`、可变 Workshop 引用和直接输出到发布目录都会制造隐藏环境依赖。它们可以在本地容忍，但发布流程应使用可配置属性或有文档的依赖缓存，并审计 staged 结果。

构建成功不等于产物成功。确认 XML、DLL、LoadFolders 和可选兼容程序集来自同一 Revision 和 Configuration。

## 发布政策与报告

说明是否需要新游戏、现有存档能否移除。破坏性变更应提供迁移或干净失败，不能静默损坏。可行时保存已发布版本的回滚产物；如果构建依赖可变本地 DLL 或无文档工具，仅有源码 Tag 不够。

完成报告列出实际运行的命令/场景、结果、跳过检查、已测版本/配置、迁移影响和剩余风险。在可以验证的地方避免使用“应该能工作”。
