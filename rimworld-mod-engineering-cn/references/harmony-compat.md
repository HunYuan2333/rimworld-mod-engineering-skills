# Harmony 与兼容性工程

## Patch 选择

- Postfix：观察或调整结果，同时保留原调用。
- Prefix：校验、准备状态或刻意跳过/替换行为。返回 `false` 意味着承担被跳过契约的全部责任。
- Finalizer：只有在失败语义明确时才用于隔离或转换异常。
- Transpiler：无稳定接缝时的最后手段；使用语义锚点，预期 IL 形状不存在时可见地失败。

不要复制整份原版方法只修改一个分支。复制会冻结上游行为并与其他 Patch 冲突。

## Patch 契约

每个 Patch 记录：

- 目标类型、方法、签名和游戏版本；
- 目的，以及浅层扩展点不足的原因；
- 目标是否为热路径、可重入或加载阶段调用；
- 必须保持的原始行为；
- 已知其他 Patch 和排序需求；
- 目标或 IL 形状变化后的安全行为。

使用唯一 Harmony ID。Priority 或 before/after 只用于有文档的依赖，不依赖偶然顺序。

## 跨 Mod 依赖

必需依赖使用直接引用并在 `About.xml` 中声明。可选集成选择：

- 条件 XML/加载目录；
- 条件兼容程序集；
- 稳定公开 API 的适配器；
- 没有稳定契约时使用狭窄、缓存的反射。

反射只解析一次，校验签名，必要时缓存委托。可选集成失败时只降级该功能，不拖垮整个 Mod。使用包 ID，不使用显示名称识别 Mod。

## 侵入性控制

深度集成有时就是功能本身。通过以下方式控制：

- 每个外部 Mod 或上游子系统一个模块；
- 集中目标发现和诊断；
- 始终加载的签名中不出现可选外部类型；
- 版本/能力检查；
- 对重复失败的可选 Hook 使用熔断；
- 测试依赖缺失、存在和发生变化的情况。

Patch 数量不是质量指标。一个全局 Pawn/战斗方法 Patch 的影响可能超过许多只针对自定义类型的 Patch。

## 兼容性妥协等级

使用能保护需求的最浅层级。层级表示成本和所需控制，不表示道德或质量等级。

| 等级 | 技术 | 常见控制 |
|---|---|---|
| 0 | 公开 Def/API/扩展点 | 契约和普通测试 |
| 1 | 条件 XML、适配器、可选程序集 | 存在/缺失矩阵和所有权声明 |
| 2 | 窄 Postfix/Prefix 或缓存的公开反射 | Patch 清单、排序诊断、优雅降级 |
| 3 | 私有访问、全局方法拦截、Def 全量重写 | 版本锚点、启动验证、来源追踪、组合测试 |
| 4 | Transpiler、方法替换、全局规则大改 | 语义锚点、可见失败、上游差异审查、明确不兼容项 |

替换范围或上游限制确实需要时可以深入，但必须记录前一级为何不能满足不变量，并定义重新评估条件。

## 扩展发现与安装

Registry 或兼容模块加载器规模扩大后，不能只定义 `CanInstall` 和 `Install`。应定义：

- 稳定 ID、版本/能力范围和所有者；
- 必需与可选依赖；
- 确定顺序和循环依赖行为；
- 重复策略和幂等性；
- 适当区分发现、验证、注册、激活和关闭；
- 逐参与者异常隔离；
- 依赖失败后的下游行为；
- 跳过、降级和失败的可见状态及原因；
- 注销，或明确的进程级寿命保证。

不要依赖已加载程序集顺序或反射类型顺序。扫描时捕获 `ReflectionTypeLoadException` 并不能隔离构造器、能力检查或安装异常。一个可选兼容模块不能阻止无关模块安装。

公开静态回调集合本身就是扩展 API。优先使用可控制身份、去重、排序、异常隔离和清理的注册入口。为兼容保留裸列表时，新用法也应通过受控包装层。

## 冲突诊断顺序

1. 用最小相关列表复现；
2. 获取完整启动日志和 Patch 列表；
3. 确认目标方法和实际 Patch 顺序；
4. 判断问题发生在 Def、类型加载、初始化、运行时、存读档还是 UI；
5. 分别移除各集成比较行为；
6. 修复契约违反或增加局部适配器，不要盲目提高 Priority。
