# Mod 类型与适度架构

按行为和风险分类，不按下载量或主观野心分类。一个 Mod 可以同时属于多种类型。以下样例均已去命名化，来自源码或发布程序集检查。

## 纯 XML 或小型内容 Mod

例如少量武器、配方、服装、研究节点或平衡补丁。

重点：稳定 Def 名、继承、本地化、配方/研究可达性、贴图路径、条件 DLC Patch 和加载错误。不要为了“看起来工程化”而引入 C#。

## UI 或 QoL Patch Mod

例如 Tab、Gizmo、覆盖层、过滤器、警报或工作流调整。

重点：保留原版语义、修补狭窄公开接缝、只缓存经测量的昂贵工作、处理分辨率/缩放/输入，并与其他 UI Patch 联测。

## 种族或派系 Mod

样例 D 涉及种族、身体、绘制、服装、PawnKind、派系、事件、商人、背景、DLC 基因、WorldPawn 和持久化组件。

重点：种族框架契约、服装/身体兼容、生成不变量、派系/世界生命周期、DLC Gate、Pawn 引用持久化以及内容包缺失时的安全行为。

## 系统或模拟 Mod

反编译样例 A 实现跨领域循环：需求驱动 AI/工作，建筑注册到地图级设施网络，网络影响心情、Hediff、事件和设置，并持久化地图状态。

可借鉴结构：`ThingComp → 注册/注销 → MapComponent → 脏网格/网络重建 → 有界 Tick`。它还展示了旧 Def/类型映射和地图/游戏销毁时清理静态缓存。这些是样例，不是强制类名。

## 战斗或规则大改

样例 E 替换战斗算法、转换 Def、自动适配内容，使用大量 Harmony，并隔离兼容程序集。

重点：明确不兼容项、确定性转换、兼容性所有权、补丁冲突诊断、新档政策、代表性 Mod 组合测试和性能分析。私有访问和宽补丁可能是替换范围的结果，但不应成为无关 Mod 的默认做法。

## 框架或库 Mod

样例 F 几乎没有直接游戏内容，主要提供扩展加载、契约、网络、UI、生命周期和可观测性。

重点：小而稳定的契约、依赖指向契约、能力/版本协商、生命周期顺序、故障隔离、诊断、示例和弃用/迁移政策。框架便利性不能覆盖游戏线程和生命周期约束。

## 高集成内容套件

反编译样例 B、C 介于内容包和大改之间：大型 XML/资源表面、持久机制、全局运行时补丁、设置和条件集成并存。

使用 [engineering-review.md](engineering-review.md) 描述侵入轮廓。不要把平衡升级或竞争性设计等同于工程质量问题；检查全局行为、耦合、持久化和失败方式是否受控。

## 扩展规模原则

- 小型：保持简单直接，直到确实出现变化或复用压力。
- 中型：按功能组织，公共基础设施保持小型。
- 大型：建立组合根、契约/适配器、兼容模块、状态所有权、迁移和验证矩阵。

代码行数只是信号。只有当文件包含多个变化原因、隐藏所有权、阻碍聚焦测试或成为合并/兼容热点时才拆分。
